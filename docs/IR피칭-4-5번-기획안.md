## 0. 먼저 — "우리 알고리즘이 좋다"를 어떻게 어필할 것인가

네가 제일 막힌 부분이 이거니까 여기부터. **성능 숫자를 나열하는 건 어필이 아니다.**
심사위원은 96%가 좋은 건지 나쁜 건지 모른다. 아래 3개 원칙으로 번역해라.

### 원칙 1 — 비교 대상을 먼저 세워라. 숫자는 그 다음이다

숫자는 혼자 있으면 무의미하고, 상대가 있으면 무기가 된다.
4·5번 전체에서 계속 되돌아올 **비교축 3개**를 슬라이드 4-1에서 미리 박아둬라.

| 축 | 남들 | 다온 |
|---|---|---|
| **시점** | 넘어진 **뒤**에 알린다 (감지) | 넘어지기 **전**에 안다 (예측) — 평균 0.8~2.1초 |
| **기준** | 전문가가 눈으로 보는 체크리스트 (문턱·전선) | 그 사람이 **실제로 걸어 다닌 동선**을 측정 |
| **평상시** | 매트를 항상 깔아둔다 / 목걸이를 항상 건다 | 평소엔 **평평한 바닥**, 필요한 순간에만 올라온다 |

이 표가 1번(사후 대응적·일상 저해형 대책의 한계)에서 던진 문제 정의에 정확히
1:1로 대응한다. **1번에서 던진 문제를 4번에서 회수하는 구조**라는 걸 말로 짚어줘라.
"앞에서 말씀드린 세 가지 한계를, 저희는 이렇게 뒤집었습니다."

### 원칙 2 — 실패를 공개해라. 그게 완성도의 증거다

이게 5번에서 제일 강력한 카드다. 학부생 팀 발표에서 거의 안 나오는 장면이기 때문에
**기술 심사위원에게 즉시 신뢰를 준다.**

- 우리는 v6(카메라 거리 정규화)를 만들었고, **두 번의 독립 실험에서 지길래 폐기했다**
  (`docs/모델-v6-실험.md`)
- 데이터를 더 넣으면 좋아질 줄 알았는데, MCF를 학습에 넣자 오경보가 6.29 → 8.14로
  **나빠져서 학습에서 뺐다** → "데이터 양보다 라벨 품질"이라는 원칙을 세웠다
- 창 길이를 3초로 늘렸더니 오경보가 30% 줄었지만 **카메라 각도 강건성은 2건 손해**를
  봤고, 그 손해를 인지한 채로 채택했다

한 줄로: **"저희는 성능이 좋은 버전을 고른 게 아니라, 어떤 버전이 좋은지 판정할
수 있는 실험 체계를 만들었습니다."**

### 원칙 3 — 지표를 생활 언어로 번역해라

| 슬라이드에 쓰는 말 | 말로 덧붙일 번역 |
|---|---|
| 오경보 3.71회 / ADL 영상 | "정상 생활 영상 한 편에 3~4번. 초기 버전은 9번이었습니다" |
| 선행시간 0.78초 | "덮개를 열고 타일을 올리는 시퀀스가 0.2초입니다. 3배 이상 여유입니다" |
| 감지 16/17 | "17번 넘어지면 16번 잡습니다. 놓친 1건이 무엇이었는지도 알고 있습니다" |
| 13ms / frame | "1초에 75장을 처리합니다. 카메라는 30장을 줍니다. 2.5배 여유" |
| 모델 1.7MB | "사진 한 장 크기입니다. 라즈베리파이에 들어갑니다" |

> **핵심 문장 (5번 마지막에 쓸 것)**
> "저희 알고리즘의 강점은 정확도 숫자가 아니라, **놓쳤을 때와 헛돌았을 때의 비용이
> 다르다는 걸 알고 그 비대칭에 맞춰 설계했다**는 점입니다.
> 헛돌면 타일이 한 번 헛펴집니다. 놓치면 고관절이 부러집니다."

# 4번 — 문제 해결 (3장)

## 슬라이드 4-1 · 개요: 두 겹의 안전망

### 헤드라인 (택 1)
- **"넘어지기 전엔 길을 바꾸고, 넘어지는 순간엔 바닥을 바꾼다"**
- "예방과 완충, 두 겹으로 설계했습니다"

### 본문 구조 — 화면을 좌우로 가른다

```
        [ 다온 앱 ]                    [ 다온 안전 타일 ]
        예방 (Prevention)              완충 (Mitigation)
        ─────────────                  ─────────────────
        낙상이 일어나기 전               낙상이 일어나는 순간
        · 동선 컨설팅 — 공간별 위험 분석    · 낙상 0.8초 전 감지
        · 실시간 감지 — 스켈레톤 중계       · 넘어지는 방향으로 타일 전개
        · 입주민 · 카메라 관리             · 평소엔 평평한 바닥
```

### 반드시 말로 해야 할 것

1. **"두 개가 별개 제품이 아니라 하나의 루프"** — 앱이 분석한 그 공간의 동선 위에
   타일을 놓고, 타일이 감지한 사건이 다시 앱으로 돌아온다. (4-3에서 다이어그램으로 회수)
2. **원칙 1의 비교표**를 여기서 띄운다. 앞의 3번(관점의 전환)과 이어붙여라 —
   "노인을 계속 감시받는 대상이 아니라 주체적으로 걸어 다니는 사람으로 봤기 때문에,
   **평소엔 아무것도 하지 않는 시스템**이 나왔습니다."

### 시각자료
- 좌/우 2분할, 가운데 양방향 화살표. 아이콘 4개(앱) + 타일 실물 렌더 1개
- 하단에 얇은 띠로 원칙 1의 비교표 3줄

## 슬라이드 4-2 · 앱: 화면으로 보는 3개 화면

> **무대는 실버타운·요양시설이다.** 사용자는 어르신 본인이나 자녀가 아니라
> **시설 관리자**다. 입주민 정보에 "호실", 카메라에 "1층 라운지"가 들어가는 이유다.
> 3번(관점의 전환)에서 어르신을 주체로 놓았다면, 4번에서는 **그 주체가 걸어 다니는
> 공간을 고치는 쪽**으로 해결책이 간다는 걸 말로 이어줘라.

### 헤드라인
**"사람을 더 붙이는 대신, 공간을 바꿉니다"**

### 구성 — 캡처 3장 + 각 캡처 아래 2줄

캡처는 실제 화면을 그대로 쓰되, **화면 안에서 심사위원이 봐야 할 한 곳에만
동그라미/화살표**를 쳐라. 3장 다 설명하지 말고 ★ 하나만 말로 깊게 설명한다.

| # | 화면 | 무엇을 하는가 | 왜 넣었는가 (한 줄) |
|---|---|---|---|
| 1 | **마이페이지** | 입주민 등록(이름·나이·호실·비고) + 카메라 스캔·등록·연결 상태 | 시설이 **현장에서 직접 운영**할 수 있다. 설치 기사가 필요 없다 |
| 2 ★ | **동선 컨설팅** | 촬영 위치별(라운지·식당·복도) 영상 업로드 → 동선 지도 + 구역별 위험 등급 + 권고 | **5-2의 핵심.** 여기서 타일 놓을 자리가 정해진다 |
| 3 | **실시간 감지** | 스켈레톤 + 위험도 + 타일 작동 상태를 관리자 화면으로 중계 | 사건이 나면 당직 데스크에 그대로 뜬다 |
| (+) | 근처 병원 조회 | 낙상 알림의 '119 신고 지원' 화면에서 시설 주소 기준 병원 검색 | 감지에서 끝나지 않고 **다음 행동까지** 이어준다 |

### 강조 포인트 — 심사위원이 "그래서 뭐가 다른데"라고 물을 지점

> **컨설팅이 '촬영 위치' 단위로 관리된다는 점을 짚어라.**
> 기존 시설 안전관리는 사고가 난 **사람**을 기록한다 — 누가 언제 넘어졌는가.
> 다온은 **공간**을 기록한다 — 라운지의 어느 동선이 위험한가.
> 사람은 계속 바뀌지만 공간은 남는다. **한 번 고치면 다음 입주민에게도 효과가 간다.**
> 이게 시설 입장에서 투자 회수가 되는 구조다. (6번 비용 절감으로 연결)

### 시각자료
- 폰/태블릿 목업 3개 가로 배치, ★ 컨설팅은 크게 / 나머지 둘은 작게
- 컨설팅 캡처는 **분석 결과 화면**(동선 선 + 위험 구역 박스 + 권고문)으로. 업로드 화면 아님
- 마이페이지 캡처는 "나의 카메라"에 **연결됨 표시가 켜진** 상태로

## 슬라이드 4-3 · 타일 원리 + 앱↔타일 데이터 흐름

이 장은 **왼쪽 절반 = 타일 하드웨어**, **오른쪽 절반 = 데이터 흐름 다이어그램**으로 나눠라.

### 왼쪽 — 타일은 어떻게 작동하는가

3D 렌더 또는 단면도 + 아래 3단계 시퀀스 그림:

```
평상시            FIRE            0.2초 후
┌────────┐      ┌────────┐      ┌────────┐
│ ▓▓▓▓▓▓ │      │ ▓╱  ╲▓ │      │ ▓ ██ ▓ │
│ 평평한  │  →   │ 덮개    │  →   │ 타일    │
│ 바닥    │      │ 먼저 열림│      │ 상승    │
└────────┘      └────────┘      └────────┘
```

말할 것 (숫자는 슬라이드에 작게, 말로 풀어서):

- 서보 **8개** = 타일 4장 + 각 타일의 덮개 4장 (PCA9685 채널 1·3·5·7 / 2·4·6·8)
- **덮개를 먼저 90도 열고 200ms 뒤에 타일을 올린다.** RESET은 정확히 역순 —
  타일 내림 → 덮개 닫음. 순서를 지키지 않으면 내려가는 타일이 닫히는 덮개에 걸린다
- **덮개가 있는 이유가 곧 제품 철학이다**: 평소엔 바닥이 평평하다. 어르신의 생활 동선에
  아무것도 추가하지 않는다 → **1번 문제 정의 "일상 저해형 대책"의 해답**
- 통신은 115200bps 줄 단위 텍스트. `FIRE 1,3` → `OK FIRE 1,3`.
  **모든 명령이 응답을 확인하고, 시리얼이 끊겨도 프로그램은 죽지 않는다**(시뮬레이션 폴백)

### 오른쪽 — 전체 데이터 흐름 (이 다이어그램 하나가 4번의 결론)

```
  [ 카메라 1대 ]  30fps RGB
        │
        ▼
  MediaPipe Pose ── 관절 33개 (2D + 3D world landmarks)
        │
        ▼
  기본 특징 7개 ── 수직/수평속도 · 2D기울기 · 각속도
        │           + 3D 몸통각도 · 폭높이비 · 어깨높이
        ▼
  시간 특징 143개 ── 0.2 / 0.5 / 1.0초 창의 평균·표준편차·범위
        │              + 추세기울기 + EWMA
        ▼
  위험 확률 ──── EWMA 평활 → 임계값 초과가 3프레임 연속
        │
        ├──────────────┐
        ▼              ▼
  방향 판정        [ 다온 웹 플랫폼 ]
  (원형통계 R)       실시간 중계 · 이벤트 기록
        │              │
        ▼              ▼
  타일 선택        [ 관리자 · 당직 데스크 ]
        │            즉시 알림 → 119 신고 지원
        │
        ▼
  FIRE 1,3 → 아두이노 → 덮개 열림 → 타일 상승
        │
        ▼
  ★ 총 소요 13ms / frame  →  낙상 0.8초 전에 이미 결정이 끝나 있다
```

### 이 장의 마무리 한 문장

> "카메라 한 대와 1.7MB짜리 모델로, 넘어지기 0.8초 전에 바닥이 바뀝니다."

# 5번 — 문제 해결 2 : 완성도와 기술적 차별점 (2장)

## 슬라이드 5-1 · 앱 ① 낙상 예측 알고리즘

### 헤드라인
**"'넘어졌다'를 알리는 기술은 이미 있습니다. 저희는 '넘어질 것 같다'를 압니다."**

### 본문 A — 왜 어려운가 (이걸 먼저 말해야 뒤의 숫자가 산다)

심사위원이 "그거 그냥 사람 쓰러지면 알아채는 거 아냐?"라고 생각하는 걸 먼저 깨라.

> **문제 1. 앉는 동작이 넘어지는 동작보다 빠르다.**
> 실측했습니다. 낙상 직전 1초의 수직속도가 0.039인데, 빠르게 앉기·물건 줍기는
> 0.071입니다. **속도만 보는 알고리즘은 구조적으로 이걸 못 가른다.**
>
> **문제 2. 카메라 쪽으로 넘어지면 2D로는 안 보인다.**
> 앞으로/뒤로 넘어질 때 화면상 기울기가 **1.3도**밖에 안 나옵니다. 몸이 화면 평면이
> 아니라 깊이 방향으로 기울기 때문입니다.
>
> **해결.** MediaPipe **3D world landmark** 기반 몸통 각도 + 폭/높이 비율 +
> 어깨 높이를 특징에 추가 → 감지율은 유지한 채 **오경보를 전 데이터셋에서 27~49% 감축.**

### 본문 B — 검증 (표 하나. 이게 완성도 항목의 본체)

**독립 데이터셋 4개, 전부 학습에 쓰지 않은 영상**

| 데이터셋 | 성격 | 낙상 감지 | 오경보 | 선행시간 |
|---|---|---|---|---|
| Le2i (26낙상/7ADL) | 국제 표준 벤치마크, 실내 4개 방 | **26/26 (100%)** | 3.71회 | 2.12초 |
| URFD (6낙상/11ADL) | 다른 연구실·다른 카메라 | **6/6 (100%)** | 2.18회 | 0.75초 |
| **자체 촬영 (17낙상/23정상)** | **실제 배포 환경**, 사람 단위 교차검증 | **16/17 (94%)** | 1.61회 | 0.78초 |
| MCF (18낙상, 8각도) | 학습 라벨을 아예 안 쓴 외부 벤치마크 | **17/18 (94%)** | — | — |

**말로 덧붙일 것 (중요):**
"세 번째 줄을 봐주십시오. 저희가 직접 찍은, 실제로 시연할 환경입니다.

### 본문 B — 그래서 우리가 바꾼 것 (기술적 차별점 2개)

**① 체류(dwell)가 아니라 동선(passage)을 잰다**

우리도 처음엔 "어디에 오래 있나"를 재는 히트맵이었다. 그런데 오래 앉아 있는

- 바운딩 박스 전체가 아니라 **발끝 좌표**(박스 하단 중앙)를 쓴다 — 사람이 실제로 딛고 선 바닥

### 본문 C — 타일: 환경의 초개인화 (컨설팅과 타일이 만나는 지점)

이게 **4번에서 말한 "하나의 루프"의 완결**이다. 여기서 반드시 명시적으로 이어라.

```
  컨설팅이 찾은 그 공간의 동선  →  타일을 놓을 자리가 결정된다
                                        ↓
                        낙상 순간, 넘어지는 "방향"으로 타일이 선택된다
```

- 시설마다 평면이 다르고, 같은 시설 안에서도 라운지와 복도의 동선이 다르다.
  그래서 "어디에 깔아야 하나"가 기존 안전매트의 진짜 문제다 —
  **다 깔면 비싸고, 조금 깔면 빗나간다**
- 다온은 **실제로 걸어 다닌 동선 위에** 놓는다. 컨설팅 리포트가 곧 시공 지시서다
- 그리고 낙상 순간에는 **방향까지 본다**: 몸통 중심의 화면상 이동 방향을
  **원형통계(circular statistics)** 로 최근 프레임에서 평균 내고, 방향 일치도 R로
  확신을 잰다
  - 방향이 확실하면 → 해당 행/열, 아주 확실한 대각이면 → 모서리 **한 장만**
  - 확신이 낮거나 수직으로 주저앉으면 → **전부 편다** (안전 쪽으로 실패)
- **발 위치를 안 쓴 이유도 말해라**: 발목 랜드마크는 가려지기 쉽고 추적이 불안정해서,
  일부러 **몸통의 이동 방향**을 썼다. "쉬운 방법이 아니라 되는 방법을 골랐다"

뒤의 항은 눈에 안 보이니까요. 저희는 영상으로 그걸 잽니다.
그리고 시설은 이 문제가 더 큽니다. 노인요양시설 안전사고의 **94.1%가 낙상**이고,
장기요양 병상 하나당 연간 1.5건이 발생합니다 — 해외 기준입니다만,
700병상 규모 시설이라면 **한 곳에서만 연간 천 건 단위**입니다.
그래서 알고리즘도 '어디 오래 있나'에서 '어디를 자주 지나나'로 다시 썼습니다.
발끝 좌표를 따라가고, 제자리 구간은 걷어내고, 몸을 돌리는 지점엔 가중치를 줍니다.
그렇게 나온 동선 위에 타일을 놓습니다. **공간마다 다르니까요.**
그리고 넘어지는 순간엔 방향까지 봐서, 확실하면 한 장만, 불확실하면 전부 폅니다.
헛돌면 타일이 헛펴집니다. 놓치면 고관절이 부러집니다. 저희는 그 비대칭에 맞춰
설계했습니다."

## 부록 B · 예상 질문 대비 (백업 슬라이드용)

| 질문 | 답 |
|---|---|
| "정확도 94%면 6%는 놓치는 거 아닌가?" | 놓치는 것과 헛도는 것의 비용이 다르다. 우리는 의도적으로 감지율 쪽에 치우친 동작점을 골랐다. 오경보는 타일이 한 번 헛펴지는 것 |
| "자체 데이터 40클립은 너무 적지 않나?" | 맞다. 2명·40클립이라 신뢰구간이 넓다. 그래서 국제 벤치마크 3개로 함께 검증했고, 다음 개선 1순위가 인원·환경 확대라고 문서에 명시했다 |
| "카메라로 노인을 감시하는 거 아닌가?" | 중계 화면에 흐르는 건 **관절 좌표 33개로 그린 스켈레톤**이지 얼굴이 아니다. 컨설팅 결과물도 개인 기록이 아니라 **공간 단위 동선 지도**다. 그리고 평소엔 타일도 바닥에 숨어 있다. 설계 전체가 '감시받지 않는 안전'이다 |
| "기존 낙상감지 매트/목걸이와 뭐가 다른가?" | 셋 다 사후다. 넘어진 걸 알린다. 우리는 넘어지기 0.8초 전에 물리적으로 개입한다. 그리고 평소에 착용하거나 밟고 다닐 게 없다 |
| "왜 딥러닝이 아니라 부스팅인가?" | Transformer 계열이 성능은 좋지만 학습 영상 240개 규모와 CPU 실시간 제약에서는 과적합·지연 위험이 크다. 논문의 핵심 통찰(시간 정보·3D 각도·신호 평활화)은 취하고 아키텍처만 제약에 맞췄다. 데이터가 늘면 GRU/Transformer가 다음 단계다 |
| "실제로 넘어질 때 타일이 사람을 다치게 하진 않나?" | 덮개를 먼저 열고 타일을 올리는 2단 시퀀스와, 방향 확신이 낮으면 전부 펴는 안전 쪽 실패 규칙이 그 대비다. 완충 효과의 정량 측정은 아직 검증 전이며 다음 단계 과제다 |
