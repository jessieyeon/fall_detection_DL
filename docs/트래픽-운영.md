# 트래픽 운영 — 측정값과 한도

전시 중 서버가 버티는지 보는 법과, 지금 한도가 왜 그 값인지.

## 지금 상태 보기

```bash
curl -s https://내주소/api/metrics | python3 -m json.tool
```

| 필드 | 무슨 뜻 | 이상 신호 |
|---|---|---|
| `requests.by_status` | 상태코드 분포 | 5xx 가 보이면 즉시 서버 로그 확인 |
| `slow_requests` | 3초 넘게 걸린 요청 누적 | 계속 늘면 인스턴스가 부족한 것 |
| `jobs.inflight` | 분석 대기+실행 중 | `max_inflight` 에 붙어 있으면 업로드가 거절되는 중 |
| `live.self_sessions` | 체험 중인 인원 | `self_max` 에 붙어 있으면 체험 버튼이 '가득 참' |
| `live.viewers` | 실시간 화면을 보는 인원 | |

개인정보는 없고 카운터만 있다. 재시작하면 0 부터 다시 센다(메모리 카운터).

## 부하 걸어 보기

```bash
python3 scripts/load_test.py https://내주소 --users 50 --seconds 60
```

가상 관람객이 로그인 → 첫 화면 → 리포트 조회 → 실시간 화면 폴링까지 실제 관람객이
하는 일을 그대로 한다. **503(거절)은 실패로 세지 않는다** — 한도를 지키느라 의도적으로
거절한 것이고 설계대로 동작했다는 증거다. 진짜 실패는 5xx 와 타임아웃이다.

단계적으로 올릴 것. 한 번에 100명으로 가면 어디서 무너졌는지 알 수 없다.

## 측정 결과

### 도구 검증 (2026-08-08, 로컬 맥북)

| 가상 관람객 | 요청 | 정상/거절/실패 | p50 | p95 | 판정 |
|---|---|---|---|---|---|
| 10 / 15초 | 128 | 128 / 0 / 0 | 0.006s | 0.054s | 정상 |

**이 숫자는 수용 한계가 아니다.** 측정 당시 이 맥북은 디스크가 99% 차 있고 v6 특징
추출이 동시에 돌고 있어서 시스템이 스왑을 치고 있었다. 여기서 확인한 것은 **도구가
동작한다는 것**뿐이다 — 부하 스크립트가 세션을 흉내내고, `/api/metrics` 카운터가
클라이언트가 센 요청 수와 일치했다(128 + 메트릭 조회 2 = 130).

### 실제 수용 한계 (배포 후 채울 것)

배포 인스턴스는 로컬 맥북과 사양이 다르다. **로컬 수치를 믿지 말 것.**

| 가상 관람객 | p50 | p95 | 실패 | 판정 |
|---|---|---|---|---|
| 10 | | | | |
| 50 | | | | |
| 150 | | | | |

**처음 p95 가 2초를 넘는 지점이 이 서버의 수용 한계다.**

동시 체험 세션(`DAON_SELF_MAX`)은 따로 잰다. 체험 세션 하나가 **초당 20회 추론**을
발생시키므로, 세션 수 × 20 이 초당 추론 횟수다. 브라우저 탭을 여러 개 열어 동시
체험하면서 게이지가 버벅이기 시작하는 지점을 찾는다.

    DAON_SELF_MAX=8 python3 -m uvicorn webservice.app:app --port 8000

## 확정한 한도

| 변수 | 현재값 | 근거 |
|---|---|---|
| `DAON_MAX_CONCURRENT_JOBS` | 2 | 동시 14건 부하에서 2건씩 짝지어 완료 확인 (2026-08-07) |
| `DAON_MAX_INFLIGHT_JOBS` | 8 | 초과분 6건이 0.0초에 즉시 503 — 기다리게 하지 않는다 |
| `DAON_SELF_MAX` | 3 | **아직 추측.** 위 측정 후 근거를 채울 것 |
| `DAON_MAX_UPLOAD_MB` | 200 | 아이폰 1분 촬영이 1080p 기준 100~150MB |
| `DAON_ANALYZE_MAX_SECONDS` | 90 | 영상 앞부분만 분석 |

## 전시 중 문제가 생기면

1. `/api/metrics` 로 **어디가** 막혔는지 먼저 본다 (분석 대기열? 체험 세션? 전체 요청?)
2. **분석이 막혔으면** — 업로드는 원래 거절되게 설계돼 있다. 관람객에게는 "지금 분석
   요청이 많습니다" 안내가 나간다. 그대로 두어도 서버는 죽지 않는다
3. **체험 세션이 가득 찼으면** — 체험 버튼이 '가득 참'으로 바뀐다. 이것도 설계된 동작이다
4. **전체가 느려졌으면** — 인스턴스를 키우는 것이 유일한 답이다. **한도를 올리면 더
   나빠진다** (동시에 도는 일이 늘어 전부 같이 느려진다)
5. 재시작하면 진행 중이던 분석 잡과 카운터가 사라진다(인메모리). 리포트는 DB 에 남는다

## 주의: 워커는 1개로 유지할 것

분석 잡 저장소와 트래픽 카운터가 모두 프로세스 메모리에 있다. uvicorn 워커를 여러 개
띄우면 폴링이 다른 워커로 가서 잡을 못 찾고, 카운터도 갈라진다.
워커를 늘려야 할 만큼 트래픽이 오면 그때 잡 상태를 DB 나 Redis 로 옮긴다.
